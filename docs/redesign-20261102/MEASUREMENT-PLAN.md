# 事業成果と行動計測の運用計画

作成日: 2026-11-02  
対象: Cyber Knock公式サイトの実装済み9イベントと問い合わせ運用  
状態: **運用設計。GA4への接続・実データ集計・対象ユーザーテストは未実施。**

## 1. 目的と現時点の境界

主目的は、有効な事業相談を増やし、その後の商談・案件化・受注につなげることである。クリック数やフォームの成功イベントだけで、問い合わせの質や事業成果を判定しない。

ソース調査では既存のGA4計測ID・gtag初期化・分析基盤の接続設定は確認できなかった。[SiteAnalytics](../../components/site-analytics.tsx) と [trackEvent](../../lib/analytics.ts) は、すでに `window.gtag` が存在する場合にだけイベントを渡す。計測ID、外部タグ、追跡cookie、ユーザー識別子を今回のコードから新規作成していない。gtagがない時点のイベントは保存・後送されない。

既存の訪問者数、CVR、有効問い合わせ数、商談化率、受注率は未取得である。「0件」ではなく「未取得」と記録する。分析APIへの新規問い合わせは本計画作成では行っていない。利用できる既存集計・ローカルキャッシュ・保存済みレポートがある場合は、所有者と期間・定義を確認してから優先利用する。

実装と検証の詳細は [問い合わせ・計測の検証記録](../redesign-2026-11-02/contact-and-analytics.md) を参照。以下の「運用する」「接続時に確認する」は今後の手順であり、データ収集済みという意味ではない。

## 2. 実装済みイベントの契約

### 2.1 全イベントに付与する属性

9イベントすべてで、`page` は送信時の `window.location.pathname` を固定分類した値になる。呼び出し側のpage指定で上書きできない。

加えて `page_location` と `page_referrer` を明示する。前者は下表の定数から生成し、後者は常に空文字。URLのquery・hash、実際の参照元、プレビューのhostnameは送らない。

| `page` | 固定の `page_location` |
|---|---|
| `home` | `https://cyberknock.pages.dev/` |
| `sports_dx` | `https://cyberknock.pages.dev/sports-dx` |
| `case_study` | `https://cyberknock.pages.dev/cases/ai-sports-trainer` |
| `security` | `https://cyberknock.pages.dev/security` |
| `privacy` | `https://cyberknock.pages.dev/privacy-policy` |
| `other` | `https://cyberknock.pages.dev/` |

未知のパスは `page: other` と固定のルートURLになる。任意のURLを分析基盤へ渡すフォールバックはない。値が未指定・許可外の属性は原則省略される。`service` 未選択を自動的に `other` へ置き換えていない。

### 2.2 9イベントの正確な名前・発火条件・追加属性

表の属性に加え、全イベントへ前節の `page / page_location / page_referrer` が付く。下表は現行コンポーネントが渡す属性であり、許可リストに存在する属性がすべてのイベントへ自動付与されるわけではない。

| イベント名 | 実装上の発火条件 | 現在渡す追加属性 | 集計時の注意 |
|---|---|---|---|
| `cta_click` | `data-track="cta_click"` を持つ要素のクリック | `location`、指定がある場合 `service` | 問い合わせ直行に加え、トップのスポーツDX詳細へのバナーも含む。全件を「フォーム到達」と呼ばない。 |
| `case_study_click` | 計測属性を付けた事例リンクのクリック | `location` | 対象は指定リンク。ヘッダー・フッターなどの未指定リンクまで網羅するイベントではない。 |
| `case_study_view` | 事例ページでSiteAnalyticsがmount、またはpathnameが事例へ変わった際のeffect | なし | 表示の入口。本文の読了、画像の視認、滞在時間は測定しない。再訪・再mountでは再発火し得る。 |
| `store_click` | 指定されたApp Store／Google Playリンクのクリック | `location / store` | 製品の確認行動。インストール、購入、アプリ利用を示さない。 |
| `contact_form_start` | フォーム内の最初のフォーカス、または未開始状態での送信操作 | `source`、選択済みなら `service` | 同じmount中は1回。入力文字の変更に限定せず、フォーム内リンクや送信ボタンへのフォーカスでも開始になり得る。 |
| `contact_form_submit` | クライアントの入力検証を通過し、POSTを試みる直前 | `source`、選択済みなら `service` | 入力エラーで止まった操作は含まない。失敗後の再試行は別イベントになる。 |
| `contact_form_success` | HTTP成功かつAPIのJSONが `ok: true` | `source`、選択済みなら `service` | API受付の代理指標。実通知の人による受領、有効相談、商談を保証しない。honeypot破棄もAPIは成功を返すため、bot等を完全に除いた営業件数ではない。 |
| `contact_form_error` | クライアント検証、HTTP失敗、通信例外、クライアントの時間切れ | `source / error_type` | 現行のerrorイベントにserviceはない。エラー文言・不正フィールド名・入力内容を渡さない。 |
| `contact_form_abandon` | 開始済み・成功前のフォームが `pagehide` を受けたとき | `source`、その時点で選択済みなら `service` | 離脱の近似。SPA内遷移、プロセス終了などを完全捕捉しない。復帰後の再pagehideで重複し得る。単独で正確な離脱率にしない。 |

`contact_form_error` の現行分類は、クライアント検証／HTTP 400が `validation`、HTTP 429が `rate_limit`、その他のHTTP失敗が `server`、クライアントAbortErrorが `timeout`、その他の通信例外が `network`。許可リストには `configuration / unknown` もあるが、現行フォームはこれらを発火させない。サーバーの設定不足HTTP 503も現在は `server` として計測される。429への表示対応は、サーバー側にレート制限が実装済みであることを意味しない。

### 2.3 許可される属性値

一次資料: [lib/analytics.ts](../../lib/analytics.ts)。許可外の属性名・値は削除する。

| 属性 | 許可値 |
|---|---|
| `location` | `header`, `hero`, `services`, `case_study`, `process`, `profile`, `footer`, `sports_dx`, `security`, `contact`, `case`, `faq`, `mobile_nav`, `content`, `unknown` |
| `service` | `sports-ai`, `product`, `ai-improvement`, `advisory`, `sports-dx`, `other` |
| `store` | `app_store`, `google_play` |
| `source` | `home`, `sports_dx`, `case_study`, `security`, `privacy`, `other` |
| `page` | `home`, `sports_dx`, `case_study`, `security`, `privacy`, `other` |
| `error_type` | `validation`, `network`, `server`, `timeout`, `rate_limit`, `configuration`, `unknown` |

`location` はクリックされた配置、`page` はイベント発生時のページ、`service` は相談テーマである。名称が似る `case / case_study`、`sports-dx / sports_dx` を集計側で勝手に変更しない。

フォームの `source` は**フォームを設置しているページ**を意味する。現在は [トップのContactForm](../../app/page.tsx) に全ページの相談が集まるため `home` となる。広告媒体、流入元、直前ページ、クリックしたCTAを推定する値ではない。通知本文の「相談元」も同じ定義である。

`service` は許可されたqueryによる事前選択、または本人の選択だけを扱う。開始時に未選択で成功時に選択された場合や、途中でテーマを変えた場合、開始と成功の分類は異なる。テーマ別イベント件数の比を、同一集団の厳密な完了率と呼ばない。空欄はレポートで「未選択」として残し、本人が選んだ `other` と分ける。

### 2.4 個人情報を送らない範囲

本実装の分析イベントには、氏名、メールアドレス、会社・組織名、相談本文、予算、入力文字、honeypot、通知本文、エラー原文、raw URL、query、hash、参照元URLを追加しない。CRMのlead ID、メールのハッシュ、問い合わせを識別できる独自IDも現時点では送信しない。これらをURL、`data-*`、イベント名、イベントラベルへ迂回して入れない。

問い合わせAPIは相談に応答するために入力内容を既存の通知先へ送る。その業務処理と、個人情報を含めない行動計測は用途・保存先を分ける。分析レポートへ相談本文や通知のスクリーンショットを貼らない。

gtagが別の設定から付ける自動イベント・ユーザープロパティ等まで、この許可リストで制御されるわけではない。将来の接続時には、自動page_view、フォームの拡張計測、外部リンク計測、タグ管理側の変数も点検する。計測を始める前に、PIIを含まないpage_viewと全訪問の分母を別途設計・検証する。現在の9イベントは、全ページの閲覧イベントを実装したものではない。

プレビューでも本実装の `page_location` は固定の本番URLになる。**page_locationだけで本番・検証トラフィックを区別しない。** 将来タグを導入するときは、実際の配信hostnameと環境に応じてタグの読み込み先を分けるか、プレビューで読み込みを停止する。

## 3. 有効相談と営業ステージの定義

小規模な事業でも更新を続けられるよう、通知の確認と営業管理を同じ担当者がつなぐ。問い合わせ数を増やすために、予算未定・仕様未定・スポーツ以外という理由だけで無効としない。

| 段階 | 記録する条件 | 数えない／別に扱うもの |
|---|---|---|
| 受信記録 | 担当者が実際の通知窓口で内容を確認できた問い合わせ | ブラウザのsuccessイベントだけ。通知到達未確認のものは受付イベントとして別記。 |
| 有効問い合わせ | 実在の相談として連絡可能で、AI・Web・モバイル・技術支援・スポーツDX等の依頼／検討課題がある | spam、営業売り込み、採用応募、重複、製品利用者の一般サポートは分類を分ける。判別前は「確認中」であり、無効に即分類しない。 |
| 商談 | 当事者間で事業・技術課題を確認する打ち合わせを実施し、内容と次の対応を記録 | 予約だけ、日程調整だけ、無断欠席。メールのみで案件化した経路はそのまま記録し、架空の商談を作らない。 |
| 案件化 | 解決したい課題、支援範囲の仮説、相談先の担当者、次の判断・提案の進め方を確認し、追跡する案件として登録 | 一方的に提案書を送っただけ、具体的な検討のない資料請求だけ。予算の確定を一律の必須条件にしない。 |
| 受注 | 発注書、契約、その他合意した方法により依頼の成立を確認 | 口頭の期待、見積提出、検討中。入金は別の実績として管理。 |
| 保留／失注／対象外 | 理由と判断日を記録 | 返信待ちを即失注にする、後から理由なく都合のよい分類へ変更すること。 |

**有効性と優先度は別の軸にする。** 有効相談について「課題の具体性」「支援範囲との適合」「検討主体・次の行動が確認できるか」を担当者が短く記録する。優先対応、追加確認、将来検討という分類で十分であり、確認できない情報を低い点数で埋めない。予算が未定でも、自治体の実証設計や新規事業の検討相談は有効になり得る。

初回確認・返信はサイトが案内する2営業日以内を運用目安とする。担当者不在時の引き継ぎと、遅れる場合の対応を事業側で決める。フォームのUXと担当者の対応速度の影響を区別するため、受信時刻・初回返信時刻も残す。

## 4. CRM／管理表と重複の扱い

### 4.1 最小の記録項目

既存CRM、またはアクセス制限した管理表を使う。新しい外部サービスを本計画だけで開設・接続しない。

| 項目 | 用途・扱い |
|---|---|
| 内部lead ID | CRM内だけの管理番号。GA4、URL、サイトイベントへ送らない。 |
| 初回受信日時／集計日 | 元日時を残し、集計はAsia/Tokyoで統一。 |
| 通知参照先／連絡先 | 対応に必要な情報は権限のあるCRM内だけ。公開レポート・リポジトリへ複製しない。 |
| フォーム設置場所／テーマ | 通知のsourceとserviceをそのまま保存。未選択は未選択。 |
| 相談対象の分類 | スポーツ企業、自治体、競技団体、新規事業、その他等、必要最小限の固定分類。 |
| 有効性／確認日／分類理由 | 有効・対象外・確認中・重複を区別。理由は集計用の短いカテゴリ。 |
| 初回返信日時 | 応答速度と未対応の確認。 |
| 商談・案件化・受注の初回日時 | 各段階に初めて到達した日。後から上書きして経緯を失わない。 |
| 案件ID／主たるlead ID | 同じ案件の複数連絡を整理。個別案件と入口相談の数を混同しない。 |
| 重複先ID／保留・失注理由 | 重複除外と、判断待ち・対象外の区別。 |
| 流入経緯の自己申告 | 会話で任意に分かった場合だけ固定カテゴリで記録。取得できなければ不明。sourceから推定しない。 |

### 4.2 重複排除

- 原則は**同一組織の同一相談案件を1件**とする。同じメールアドレスだけで機械的に統合しない。同じ組織でも独立した案件なら別件。
- 再送信、別担当者からの同一案件、タイムアウト後の再送は、担当者が内容を照合して最初の有効な記録へ関連付ける。初回受信日を維持し、元の受信記録は監査用に残す。
- 分割・統合した場合は日付・理由・関連IDを残す。集計の遡及修正も履歴に記録する。
- 1案件に複数のleadが関連するとき、受注件数は案件IDで1回だけ数える。入口別の転換集計には主たるleadを1つ指定し、同じ受注を重複加算しない。
- サーバーに永続的な重複送信防止・キューは現在ない。クライアントの連打抑制を、営業記録の重複排除の代替にしない。

### 4.3 分析イベントと営業記録の接続

通知→CRMは、担当者が権限のある業務記録内で照合して内部lead IDを付ける。氏名・メール・本文を分析イベントへ送って結合する方法は使わない。

現行コードは、ブラウザの識別子、セッションID、CTA帰属キー、lead IDを問い合わせAPIへ渡していない。したがって、特定のCTAクリックと特定の受注の個人単位の結合はできない。時刻が近いという理由だけでも同一人物と推定しない。

当面は次の2表を、同じ期間・テーマ・定義バージョンで並べる。

1. 計測できたWeb行動の集計: ページ・配置・テーマ別のクリック、フォーム開始、送信試行、成功。
2. CRMの営業集計: 重複を除いた受信、有効相談、商談、案件化、受注、保留・失注。

この比較は経路別の厳密な受注帰属ではない。「事例を見た人の受注率」と断定するには、別途適切な計測設計が必要。連絡先のハッシュや追跡storageを追加することを本計画の前提にしない。

## 5. KPIと分母

### 5.1 優先指標

| 指標 | 定義・分母 | 現在の取得可否 |
|---|---|---|
| 有効問い合わせ数 | 指定期間に初回受信した、重複除外後の有効lead数。確認中・対象外・重複を併記。 | 実通知確認とCRM運用が必要。履歴値未取得。 |
| 訪問者→問い合わせCVR | 同じ観測窓で、計測できた訪問者のうちsuccessが観測されたユニーク利用者数 ÷ 計測できた訪問者数。識別方法を固定する。 | GA等の訪問者分母が未接続。現在算出不可。有効相談ではなく「観測フォーム成功」のCVR。 |
| 有効問い合わせ→商談 | 同じ初回受信コホートの有効leadのうち、実施済み商談があるlead数 ÷ 有効lead数。 | CRMの日時記録から算出。未取得。 |
| 商談→案件化 | 同じコホートで商談済みかつ案件化したlead数 ÷ 商談済みlead数。 | CRMから算出。商談を経ない案件化は別経路として併記。 |
| 案件化→受注 | 同じコホートの案件化した主たるlead／案件のうち受注した数 ÷ 案件化数。案件の重複を排除。 | CRMから算出。未取得。 |
| 商談→受注 | 同じコホートで商談済みかつ受注したlead数 ÷ 商談済みlead数。 | CRMから算出。未取得。 |

**有効問い合わせの訪問者CVRは、現在の実装では厳密に算出できない。** CRMの有効件数と分析基盤の訪問者は個別に対応せず、計測拒否・広告ブロック・別端末・別日にまたがる行動もあり得る。参考として「有効件数÷観測訪問者数」を併記する場合は、異なる母集団を使う営業件数密度と明示し、観測ユーザーの有効CVRや因果効果とは呼ばない。

分析基盤の「訪問者」は、その基盤が同じ設定で識別できるブラウザ等の単位であり、実在する人の完全な人数ではない。ユーザー単位とセッション単位を同じグラフや比率で混ぜない。

### 5.2 補助指標

セッション識別を利用できる分析基盤に接続できた場合は、同一セッション内の重複を除いて計算する。現行イベント自体に独自セッションIDを追加したわけではない。

| 指標 | 推奨の定義 | 制約 |
|---|---|---|
| トップの主CTAクリック率 | `page=home, location=hero` のcta_clickがあるセッション数 ÷ トップを閲覧したセッション数 | CTAの視認を直接計測するイベントはないため、厳密な表示回数CTRではなくトップ訪問を分母とする代理指標。 |
| 事例への遷移 | 指定の入口でcase_study_clickがあるセッション数 ÷ その入口ページのセッション数 | 未計測リンク経由・直流入は別。case_study_viewも併記し、本文理解と混同しない。 |
| フォーム開始率 | contact_form_startがあるセッション数 ÷ トップを閲覧したセッション数 | フォームの実視認回数は取得していない。訪問を分母とする値と明示。 |
| フォーム完了率 | start後にsuccessが観測されたセッション数 ÷ startがあるセッション数 | 期間末の進行中セッションを確定後に集計。フォーム未変更でもフォーカスだけで開始になる。 |
| 送信試行後の成功割合 | submit後にsuccessがあるセッション数 ÷ submitがあるセッション数 | APIリクエスト1回ごとの厳密な成功率ではない。再試行を含む。 |
| エラー経験率 | errorがあるセッション数 ÷ startがあるセッション数 | error_type別に確認。errorイベントにserviceがない点を守る。 |
| 未完了セッション割合 | startがあり、集計確定時点までにsuccessがないセッション数 ÷ startがあるセッション数 | 同一セッションを追える場合に限る。厳密な心理的離脱とは限らない。 |
| pagehideによる離脱信号 | contact_form_abandonの件数と、観測できる場合のセッション重複除外数 | 未完了セッション割合と別欄。pagehide欠損・復帰・再発火の影響がある。 |
| テーマ別の相談関心 | service別のCTA、開始、送信試行、成功、有効lead件数 | 開始後のテーマ変更があるため、単純な成功件数÷開始件数を同一テーマの完了率として扱わない。 |
| 公開製品の確認 | store_clickをstore・page・location別に集計 | 購入・インストール成果ではない。 |

イベント件数しか利用できずセッションを重複排除できない場合は、件数と分類だけを報告し、正確なユーザー／セッション転換率を作らない。reload、戻る、別タブ、再試行、gtag読み込み前の取りこぼしを検証ログに残す。

トップの `page=home, location=services, service=sports-dx` は、現行ではスポーツDX詳細へ進むバナー。問い合わせ直行のCTAとは分けて集計する。CTA属性が変わる場合は、この分類表と計測定義も同時に更新する。

## 6. 期間、コホート、判定方法

### 6.1 集計の基本

- 基準タイムゾーンはAsia/Tokyo。初回受信日時、イベント期間、公開日時の扱いを揃える。
- 営業件数は週次で確認し、月次は**初回受信月のコホート**で追う。商談月・受注月の実績表は別に作り、同じ月の受注件数を同じ月の新規問い合わせ数で割らない。
- 月末近くに受信した相談と数か月前の相談を同じ成熟度として比較しない。各コホートに集計基準日と経過日数を表示する。
- 初期の観測窓は受信から30日・90日・180日を提案する。これは業界の標準値という主張ではなく、短期の商談と長い実証・発注判断を分ける運用上の設定。最初に事業者が採用する窓を確定し、途中で都合よく変えない。
- 各窓で、有効・商談・案件化・受注の件数と段階間の共通集合を集計する。商談を経ない案件を商談分母へ加えない。観測窓外で進んだ案件は累積実績として別記する。
- 分母が0なら率は「算出不可」。少数件では分子／分母も表示し、割合だけを大きく見せない。確認中件数・継続中件数を残す。

### 6.2 改善判定

公開前の同じ定義の実測がない場合、公開後の最初の完全な集計期間を基準にする。「改善前に比べ何%増えた」と後から推計しない。

最初の4週間は計測の欠損・分類の一貫性・有効相談の内容を確認し、その後も母数と営業期間に応じて観測を続ける。4週間経っただけで成果改善を断定しない。比較時は期間長、曜日構成、流入の構成、広告・営業活動、季節、公募時期、代表者の応答時間、サイト変更履歴を併記する。

有効相談の増加に加え、商談化率、対象外・spamの比率、対応工数を見る。総問い合わせ数だけ増えて有効相談が増えない場合、コピー・対象者説明・問い合わせ案内を見直す。フォームを厳しくして母数を小さくしただけの率上昇も成功としない。

十分な母数があるときだけ、事前に決めた差と不確実性を評価する。小さなサイトで短期間のA/Bテストを必須にせず、対象者テストと実際の相談理由を合わせて判断する。受賞可能性やAIレビューの点数は営業KPIの代理にしない。

## 7. 公開・計測接続時の確認手順

本番公開は明示的な承認後に行う。ここでは手順を定義するだけで、公開・新規タグ接続・実通知は実行していない。

| 順序 | 担当・作業 | 残す証拠／完了条件 |
|---|---|---|
| 1 | 事業者: 利用可能な既存分析基盤と管理権限、保存済み集計、公開予定commitを確認 | 未取得を0にしない。取得済みデータの期間・定義・時点を記録。 |
| 2 | 実装担当: 9イベントと許可属性が計画と一致するか、テスト・型検査・buildを実行 | 実行commit、コマンド、成功／失敗。変更があれば定義表も更新。 |
| 3 | 実装担当: ローカルモックで入力エラー、送信中、成功、失敗、再試行を確認 | 実通知を発生させない。入力保持と重複抑制、successの条件を確認。 |
| 4 | 実装担当: 一時的なメモリ内gtag stub等でイベント引数を確認 | 氏名・メール等のテスト文字列、任意のquery/referrer、未許可値がイベントに含まれないこと。実際の個人情報をテストに使わない。 |
| 5 | 計測管理者: 所有者が確認した既存ID／収集先で接続を準備 | 任意のIDを発明しない。プレビューを本番に混入させず、サイトの同意・データ取り扱い方針に合わせる。接続コードは現行実装に含まれていない。 |
| 6 | 計測管理者: 自動イベントと全ページ閲覧の分母を点検 | 自動page_view・拡張計測・タグ変数も含めてURLやフォーム情報の流出がないこと。現在の9イベントだけで全訪問分母があるとみなさない。 |
| 7 | 計測管理者: 管理画面の受信確認とNetwork確認 | event名・page・location・service・store・source・error_type、固定URL／空referrerを確認。検証用収集先または検証トラフィックを除外する運用を用意。 |
| 8 | 実装担当: ページ遷移・再訪・query変更・戻るを確認 | 開始の一度だけの発火、成功後のabandon抑止、テーマ変更、事例viewの再発火範囲を記録。gtag読み込み前のイベントは後送されない。 |
| 9 | 事業者・実装担当: Functionsと静的ファイルを同じリリースでプレビュー確認 | 新UIがprivacy値を送ること。旧UI／新APIの混在を防ぎ、環境ごとの通知設定を確認。 |
| 10 | 事業者: 実通知の到達確認を行う場合、送信内容・宛先・受信者の了承を得た1件を区別して確認 | 現時点で未検証。モック成功を実通知受領と扱わない。確認したテスト通知は営業件数から除外。 |
| 11 | 承認済み公開後: 変更commit、時刻、計測開始時点、定義版を記録 | 公開承認と配信対象を一致させる。公開直後はタグ有無・送信エラー・リンク等を確認。 |
| 12 | 初日〜週次: 受信と行動件数の不自然な差を確認 | 生イベント数とCRM件数の完全一致は期待しない。bot、計測拒否、再送、通知障害、時差を切り分ける。 |

本実装では追加の `form_view`、`cta_impression`、`generate_lead`、`purchase` 等は実装していない。管理画面でsuccessを重要なイベントとして扱う場合も、「有効相談」「受注」と名称を取り違えない。

分析APIを使う運用を後から導入する場合は、期間・プロパティ・フィルタ・定義バージョンをキーに集計を保存する。更新が必要な期間だけを取得し、同じ分析データの繰り返し取得を避ける。CRMの生の個人情報をリポジトリや公開成果物へ保存しない。

## 8. 検証する改善仮説

| 仮説 | 主な経路 | 確認する指標・証拠 |
|---|---|---|
| 提供範囲と自社運用経験を初期画面に集約すると、依頼できることを早く理解できる | トップ→相談／事例 | 10秒理解テスト、トップ主CTA、事例遷移。有効相談の内容が対象領域と合うか。 |
| 実UIと品質・コストの具体的な設計判断が、技術パートナー選定の不安を減らす | 事例→相談 | 事例からのCTA、商談時の任意の相談理由、実績の理解。外部ストアクリックだけで信頼獲得を断定しない。 |
| スポーツで強みを示しつつWeb・モバイル・AI改善を分けると、関連相談の取りこぼしを減らせる | サービス別CTA→テーマ選択済みフォーム | service別の関心と有効相談。スポーツ以外の問い合わせが対象外ばかりになっていないか。 |
| 実証の成果物・判断材料を示すと、自治体や団体が初期相談を始めやすい | スポーツDX→フォーム | DXの相談CTA、sports-dxの受信内容、商談時の準備負担。source=homeをDX流入なしと誤読しない。 |
| 任意の予算・明確なエラー・失敗時保持で、検討初期の有効な相談を失いにくくなる | 開始→送信試行→成功 | 全体のセッション完了率、error_type、予算未定の有効相談、モバイルの操作観察。 |
| データ文書の要約と帰路が、確認後の相談を妨げない | データ／privacy確認→フォーム | タスク観察と疑問の解消。文書への全回遊・入力復帰を現行イベントだけで厳密に追えるとはしない。 |

これは期待する方向の仮説であり、公開前の成果保証ではない。固定したKPI定義と実際の相談記録で反証できるようにする。

## 9. 対象者5名・10秒理解テスト

### 9.1 対象と準備

実際に外注・技術支援を検討し得る対象者を5名集める。例として、スポーツ企業・新規事業担当2名、自治体担当1名、競技団体担当1名、関連領域のWeb／モバイル・AI担当1名。採用した構成と各人の役割を記録する。自社制作者やAIペルソナを、実対象者の人数に置き換えない。

日常使う端末を優先し、モバイルとデスクトップを含める。端末・ブラウザ・表示幅、対象commit／URLを記録。参加・録画・発言記録は本人の了承を得て、記録はP01〜P05の識別番号を使う。分析イベントへ参加者情報を送らない。

元サイトと変更後を同じ人に続けて見せると学習が入るため、初見テストの比較は別の参加者群を使う。5名だけの結果を統計的なCVR改善と扱わない。

### 9.2 一次テスト: 10秒以内に説明できるか

1. 事前説明は「このサイトが誰のためのもので、何を依頼できるか、分かった時点で言葉にしてください」に統一する。事業名・強み・正答例を教えない。
2. トップの初期画面を提示し、主見出しが見える時点を計時開始とする。読み込み待ち時間は別に記録する。初期画面の理解を測るため、スクロールや他ページへの移動はこの10秒間行わない。
3. 10秒までの発言を記録し、次の2条件を両方満たした時刻を記録する。
4. 10秒で画面を隠す。未回答・誤認がある場合は、その後に自由な想起を聞く。ただし、10秒後の回答を一次テストの成功へ繰り上げない。
5. 誘導しない補助質問として「何がほかと違いそうでしたか」を聞く。自社アプリの企画・開発・運用経験に気づいたかを別項目にする。

**一次テストの正答基準**

- 対象: スポーツ企業、自治体、競技団体、新規事業チーム等の事業者に向けた開発・技術支援だと説明できる。すべての対象を暗記する必要はない。
- 依頼内容: AI／動画分析、Web・モバイル開発、新規プロダクト、AI改善、実証・技術支援のうち少なくとも1つを具体的に説明できる。「アプリを使う／買うサイト」だけ、または「AIの会社」だけでは満たさない。

事前にこの基準を固定し、**5名中4名以上が両条件を10秒以内に満たす**ことを今回の理解度目標とする。5名中4名という小標本の結果は、その参加者群での観察結果である。一般の訪問者の80%が理解するという推計にはしない。

録画を利用できる場合は2名の評価者が基準に沿って判定し、不一致の理由を残す。1名しか評価できなかった場合は、その事実を記載する。採点者は参加者へ正答を促さない。

### 9.3 続く導線・安心・フォームの確認

一次テストが終わってから、普段の操作を許可する。次のタスクを役割に合わせて行う。

- 発注判断のため、自社で開発・運用している証拠と、担当範囲を探す。
- 自分の案件を相談するとしたらどこへ進むか、実際に選ぶ。
- 予算や仕様が未定の状態で相談を始められるか確認する。
- データの扱いで気になる点を探し、その後相談へ戻る。

フォームの成功・失敗テストはモックのあるローカルQA環境で行い、用意した架空のテスト情報を使う。実際のメールアドレスや機密情報を入力してもらわず、公開サイトへテスト相談を送らない。所要時間、ためらい、誤クリック、読み飛ばした情報、未解消の不安を記録する。利用者の言葉と評価者の解釈を分ける。

## 10. 担当と定例運用

| タイミング | 作業 | 担当 |
|---|---|---|
| 受信後・各営業日 | 受信確認、重複整理、2営業日以内の返信、確認中／有効の分類 | 代表者または指定した営業担当 |
| 週次 | 未対応、フォーム障害、テーマ別の有効相談、対象外理由、データ欠損 | 事業担当＋Web担当 |
| 月次 | コホート別商談・案件化・受注、応答速度、変更履歴との比較 | 事業担当 |

| 十分なデータが集まった時点 | 仮説を支持／反証する証拠と次の改善を判断 | 事業担当＋UX担当 |

ダッシュボードに最低限残す項目は、集計期間、基準日、定義バージョン、分子・分母、未取得／未確定、除外ルール、対象commit、次の判断である。担当者が実在しない体制や、未実施の定例を実績として記載しない。
