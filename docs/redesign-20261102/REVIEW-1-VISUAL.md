## 評価条件と限界

参照した証拠は、共有リポジトリの `docs/redesign-20261102/cycle-1/` にあるDesktop／Mobileの5主要ページのスクリーンショット、および既存ソースと実アプリ素材。長い画像は内容を改変せず、縦方向に切り出して読んだ。

変更前は `before/home-1440.jpg`、`home-390.jpg`、`case-390.jpg`、`sports-dx-390.jpg`、`security-390.jpg`、`privacy-390.jpg` を目視比較した。変更前のfullpageに見える空白を、コンテンツ自体が存在しない証拠とは扱わない。スクロール表示・lazy loadingが撮影時に発火していない可能性がある。

今回のfullpage取得は内部の横寸法が変化する症状があり、rootが確認済み。全体構成、内容、画像と見出しの関係の証拠として使用し、右端の約15px切れをCSSの横溢れとは判定しない。横幅の厳密な合否は、指定viewport→DOM寸法採取→viewport screenshotで再検証する。

これは実装担当とは別のAIエージェントによるレビューで、実ユーザーテストではない。なおsecurity／privacyの文章保持とページ構成は本レビュアーが実装したため、その2ページについては独立性に制限がある。実端末・Lighthouse・Core Web Vitals・実通知先への到達は本レビューでは未検証。

## 判定

**初版は完成扱いにしない。90点達成の証拠はない。**

紙色／インク／tealと実アプリ画面を軸に、情報と導線の統一が進んだ。一方、共通プロダクトビジュアルで実績名が端末画像に隠れる、スポーツDXの狭い左列で見出しが不自然に分割される、重要な補助情報がモバイルで小さい、といった修正可能な問題が実画像から確認できる。

## 4つの視点からのレビュー

### 1. クリエイティブディレクター

新しいカラーパレット、実UI、罫線、観測点／反復線、余白の扱いには一貫性がある。濃色の旧ページと無装飾のprivacyが分断されていた状態は解消した。Hero、事例、フォーム、footerの視覚的な優先順位も見える。

ただし実績ビジュアルの見せ場に重なりが残り、文字情報を犠牲にしている。背景の反復線はCyber Knockの運用改善を示す意図があるが、今の画面だけではその意味を読み取るのが難しい。大見出し、細い罫線、淡色ブロック、端末モックアップという一般的な構成を、固有のプロダクトの判断や改善過程へさらに結びつける余地がある。受賞水準の独創性9/10を付ける段階ではない。

下層Heroと本文内h3は細いウェイトで、太いh2よりも弱く見える箇所がある。特にスポーツDXの左列h2は大きさと列幅が適合していない。

### 2. UXリサーチャー

Heroに相談と事例の2導線があり、どちらが主かは明確。支援内容は対象・課題・範囲・成果物を揃え、予算未定の相談を許容している。privacyの共通ナビゲーション・目次・本文幅は変更前より明確に改善した。

一方、Heroの大見出し自体は一般的なプロダクト開発の価値であり、依頼できる仕事や自社運用経験は小さいeyebrow／説明に依存する。モバイルでは10〜11pxの対象顧客表示やeyebrowが、この重要性に対して小さい。自社アプリの名称を説明にも入れれば、画像が下に続いても実績の存在が伝わる。

ケースHeroのCTA「この経験を、自社の開発に」は相談へ進む行動を明示していない。モバイルのケースギャラリーは画像の内容を理解するには縮小が強い。タップ拡大を追加する前に、本文中の縦長画像の高さを確保したい。

### 3. 技術QA

スクリーンショット上、通常のフォーム項目、同意、送信ボタン、目次、関連リンクは識別できる。意味構造、エラー処理、reduced motion、PIIを送らない固定語彙のイベント、APIの検証はコードレビューで確認済み。ただしこれをブラウザ操作成功やWCAG適合の証明と混同しない。

プロダクトのcaption遮蔽はviewport画像で確認できる。fullpageの右切れは撮影条件の変動があるため、CSS不具合として採点しない。ケース3枚目とDX実績画像の一部fullpageではlazy loading前の空白があり、実際にその場所へスクロールして画像のロードを確認する必要がある。

### 4. BtoB発注担当者

「作れる」だけでなく、課金・品質・利用導線・待ち時間・AIコストを扱った経験が書かれていることは発注判断に役立つ。自治体向けページでは成果物と評価内容、予算／仕様が未確定な場合の進め方まで分かる。架空の導入先や定量成果を足していない点も適切。

その根拠となる実アプリの名称がメインビジュアルで隠れている点は、信頼の導線を弱める。フォームのsourceがhomeに集約される計測上の限界も残る。公開後の有効リードの分析では、テーマと元のページを区別できる設計が望ましい。

## 採点の主な根拠

- **ビジュアル6〜7.5**：共通トークン、罫線、余白、実画面は揃う。V1／V2が未解消のページは低くする。文書ページは重なりがなく読み進められるが、見出しのウェイト／Mobileの目次量に改善余地。
- **独創性6〜7**：独自マーク、実アプリ、反復線という素材はあるが、後半は一般的な罫線・カード・淡色ブロックが中心。運用経験が固有の視覚体験として十分に表現されているとはまだ言えない。
- **価値提案8〜8.5**：対象／課題／成果物は具体的。homeの3〜5秒理解は小さい補助情報へ依存。実ユーザーでの達成は未測定。
- **信頼7.5〜8.5**：実UI、ストア、担当範囲、事業者、データ方針は確認可能な形で存在。実績名の遮蔽、画像縮小、データ運用の本番再検証未実施を考慮。
- **問い合わせUX7〜8**：明確な主CTA、任意予算、少ない必須項目、通常フォームの読みやすさ。V4と流入元計測の限界、実通知先への未検証を残す。
- **情報設計7.5〜8.5**：home→case→contact、DX→contact、policy→securityを構成として追える。段階的な説明と目次がある。DX狭列の分断は読み進め方を妨げる。
